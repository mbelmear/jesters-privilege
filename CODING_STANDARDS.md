# Coding Standards

How code in this repo is written. `/code-review` checks every change against this file, alongside the working rules in `AGENTS.md` (vocabulary, test-first, content files, reduced motion), which apply in full and aren't repeated here.

## Enforced by tooling

These are non-negotiable, and a commit or pull request that breaks them is refused before review:

- **Tests are green.** The commit and merge hooks and CI run Jest; CI also runs Playwright and Lighthouse. Logic in `src/lib/` keeps at least 90% line coverage.
- **No `any`, explicit or implicit.** `strict` TypeScript rejects implicit `any`; ESLint rejects written `any`, any value that carries `any` in from a library (`JSON.parse`, `response.json()`), non-null assertions (`!`), and type assertions other than `as const` outside tests.
- **Formatting.** Prettier, checked in CI.
- **Colors and fonts come from design tokens.** ESLint rejects literal colors (hex, `rgb()`/`hsl()`/`oklch()` and friends), Tailwind's built-in palette (`bg-black`, `text-red-500`), Tailwind arbitrary color and font-family values, and inline `font`/`fontFamily` styles anywhere in `src/` outside tests. It also rejects `text-brand`: orange text uses `text-brand-display` (large) or `text-brand-ink` (small). Tokens live in `src/app/globals.css`.
- **No empty-text assertions.** ESLint rejects `toHaveTextContent("")` in Jest and `toContainText("")` in Playwright, which pass whatever the element holds; an empty element is checked with `toBeEmptyDOMElement()` or `toBeEmpty()`.
- **Browser tests poll for at least a second.** ESLint rejects a sub-second `expect.poll` timeout in `e2e/`.
- **No invisible whitespace.** ESLint rejects a literal byte order mark, no-break space, or other irregular whitespace anywhere in a file, strings, regexes, and comments included. In code, write it as an escape (`\uFEFF`, `\u00a0`).

Reviewers skip these; the rules below are the ones that need judgement.

## TypeScript

- **Outside data enters as `unknown` and is narrowed at the boundary.** The boundaries are the feed text, Transcript WebVTT, the Submit request body, anything read from `localStorage`, and `catch` variables. A validator or type guard at that boundary turns `unknown` into a domain type or throws a descriptive error; past the boundary, code works only with domain types. `Array.isArray` and `Object.entries` on an unknown value give `any`, which lint can miss; annotate their results as `unknown[]` and `[string, unknown][]`. `unknown` that leaves its boundary validator (the receiving function and the non-exported helpers it calls) is a finding.
- **Domain concepts get named types in `GLOSSARY.md` vocabulary**: `Episode`, `Fool`, `Jester`, `Submission`. A closed set is a union of string literals (`"question" | "confession" | "topic-idea" | "other"`), with one exported list as the source of truth for code that iterates it.
- **Illegal states are unrepresentable.** State with modes (the player store, the Submit form) is a discriminated union, where each variant carries exactly the fields that mode has, in place of booleans plus optional fields.
- **Switches over a union are exhaustive**, ending in a `never` check so a new variant fails to compile everywhere it needs handling.
- **Failures are loud.** A module that can't do its job throws an error that names what was wrong and where (the Feed names the Episode and the rule it broke). Fallbacks exist only where the spec asks for them, such as the monogram shield for a missing photo. Automation counts: a workflow or script that recovers on its own (retries, rebuilds, redeploys) is a fallback, and one on a schedule fails the run instead, since a silent repeat every few hours is a failure nobody sees. #18's feed check first rebuilt whenever the live build manifest couldn't be read, which a manifest GitHub's runners can never reach would turn into 12 deploys a day without a failure email. A scheduled run that tolerates one item's failure (an app's lookup, an Episode's Transcript) still names it as a `::warning::` annotation, which shows on the run's summary; a plain log line is read by nobody. #121's feed check first logged an unreadable Transcript as a plain line, so a broken `transcripts` branch would have left pages unrebuilt with no sign.
- **Logic is pure and I/O is injected.** Modules in `src/lib/` take inputs and return outputs; the clock, network, audio element, email sender, and Turnstile verifier come in as parameters or adapters, so tests pass fakes.

## React

- **Server Components by default.** `"use client"` goes on the smallest component that needs state, effects, or browser APIs, as far down the tree as it can sit.
- **Components receive what they show.** Copy and data arrive through props from content files or the Feed; a component holds presentation and interaction only.
- **The player store is the only owner of playback.** Archive rows, Episode pages, the Transcript, and the player UI send commands to the store and render its state; only the audio adapter touches the `<audio>` element. The audio element is the source of truth for an Episode's length and for reaching its end; the Feed's `durationSeconds` is a placeholder until the element reports its own.
- **Derive during render.** A value computable from props or state is computed where it's used. Effects are for syncing with something outside React (the audio element, `localStorage`, the theme on `<html>`).
- **Semantic HTML first.** Native elements (`button`, `a`, `nav`, `dialog`, headings in order) carry the behaviour; ARIA fills gaps no element covers. Every interactive element is reachable by keyboard and shows focus.
- **A control that takes its own region away sends focus somewhere deliberate**, usually the page's content (`<main>`, without scrolling), the control that opened it, or the control that replaces it, so keyboard and screen-reader users keep their place. #118's × on the player first left focus on `<body>`, as the resume offer's "Not now" and Play already did; Play now hands focus to the bar's Pause.
- **A form works before React runs.** The static HTML arrives first, so its fields are disabled until hydration (a `<fieldset>` whose `disabled` follows a hydration flag, as `src/components/submit-form.tsx` does): text typed earlier is wiped when React takes over, and a submit button posts the form natively, putting what was typed in the address bar. Its browser test is the blocked-scripts check in `docs/testing.md` (Browser tests). #27's form lost a test's message this way, only under a loaded machine.
- **Lists are keyed by identity**: a stable id such as the Episode number, never array index.
- **Images go through `next/image` with real dimensions** and alt text that says what the picture shows (for a Fool's painting: who, and what they're doing). An image shown only in one theme or at one breakpoint loads lazily, so the hidden ones are never fetched: an eager image downloads even while CSS hides it, and every early byte counts against the page's Lighthouse budget.
- **A page reads `content` inside its component**, keeping only what `metadata` needs at module scope, so a test can swap a record with `jest.replaceProperty`. #26's About page read the Jesters at module load, and the swap silently did nothing.
- **A page passes every content value it shows, metadata and the site shell (`content.shell`) included, to `<DraftRibbon uses={…}>`.** A value left out hides its drafts from the preview ribbon. The root layout renders no ribbon of its own, so each page has exactly one.
- **A library loads only where it's used.** A client library's provider wraps the sections that need it, never the root layout unless every page does: whatever the layout imports ships on every page and counts against the home page's Lighthouse budget. The same holds for any component: its client imports ship on every page that renders it, whether or not the branch using them renders there. Where pages pick between alternatives, such as the hero's reveal or simple story, the page passes its choice in as `children`, so only that page imports it.
- **A client component in the root layout receives only the fields it shows.** Its props are serialized into every page's document, so they count against every page's Lighthouse budget like its code does (docs/testing.md, Performance, has #19's case). Pick the fields in the layout.
- **UI on every page loads its animation on first use.** `MotionProvider` fetches Motion as soon as it mounts, so a part of the shell (the mobile menu, the player) mounts it only on a visitor's first interaction with that part, as `src/components/mobile-menu.tsx` does with its lazily loaded panel.
- **Animation goes through `MotionProvider`.** Animated sections use `m` components inside `src/components/motion-provider.tsx`, which loads Motion on demand, carries the reduced-motion setting, and applies the shared presets from `src/lib/motion.ts`. One exception: an ambient, non-interactive loop (a painting band's slow zoom) may be a CSS keyframe defined in `globals.css` and applied under `motion-safe:`, so a Server Component animates without shipping Motion.
- **A route over Episodes builds a placeholder page when the Feed is empty.** A static export refuses a route whose `generateStaticParams` returns nothing, and the Feed may hold no Episodes. The route builds one `noindex` address that shows the 404 page, as `src/app/episodes/[...address]/page.tsx` does; a set that can be empty while others aren't (bonus Episodes alone) shares a catch-all route with one that isn't.
- **What the build manifest records comes from the same read as the pages it describes.** Next renders pages and routes in several worker processes (past 25 pages it starts another, `staticGenerationMinPagesPerWorker`), so a module-level cache holds one per worker, and a network read made in each can succeed in one and fail in another. A live read that both the pages and `/build-manifest.json` depend on runs once before `next build` and every worker reads its snapshot, as `npm run lookups` does for Episode Listen links. #119 first looked Apple up in each worker: a lookup that failed in one would leave a page linking to the show while the manifest recorded the Episode's own link, and the feed check would never rebuild it.

## Performance

- **A change to the first screen shows its cost.** A diff that touches the header, the footer, the root layout, or what a page fetches before its first paint comes with `npm run lighthouse:compare` output against main, for each page it affects (`docs/testing.md`, Performance). Without that output, it is a finding. Early bytes that grew need a reason. A single `npm run lighthouse` run isn't enough, since its simulated times shift by up to half a second with the machine's load.
- **One page's styling stays out of every page's stylesheet.** Tailwind compiles every utility the site uses into one stylesheet that every page loads before its first paint. A utility family new to the site (mask, gradient, transition, filter) brings its rules and custom properties with it, a few hundred bytes gzipped, paid by every page for an effect one section shows. A one-section effect uses utilities the site already compiles, or an inline `style` on that section (`docs/testing.md`, Performance, has #23's case). Whether a utility is compiled is read from `lighthouse:compare`, which prints every rule a change adds to the stylesheets a page loads before its first paint. Tailwind compiles any class name it finds in a scanned file, comments and strings included, so `globals.css` scans `src/` (Jest tests included) without its Markdown (#26: when it scanned the whole repo, the colours the lint config bans reached every page's stylesheet from this file's examples). CSS modules wait on #92: `next.config.ts` builds `*.module.css` as global CSS with no class names.

## Content

- **History is told as the sources tell it.** A Fool's dates, placard (artist, title, year, medium, collection), and story agree with the painting's Commons page and the collection holding it; where those disagree or attribute loosely, the placard says so ("Attributed to", "School of", "c."). An anecdote the sources give as legend is told as one ("the story goes", "is said to"), and a quotation is one the sources print. Fools' jests, facts, and respellings trace to `docs/research/fools-jests-and-pronunciations.md`. A fact-check accounts for every claim in the copy it checks: supported, unsupported (with what the sources say), or unchecked; #120's first list missed four claims. #25's review found a drawing dated after its sitter's death shown as his face, a consultant Rabelais never wrote, and a painting credited to the museum that shows it rather than the foundation that owns it.
- **Copy expands the landing page.** Draft copy uses the landing page's metaphor and vocabulary (the King who needs no jester, the church dearly loved yet able to wander, her courtiers, fools for Christ, the motley), and never contradicts it or approved copy: the copy principle in `docs/spec.md`, Content. Approved About copy says the jester "sought no office", so #103 took "office" out of the Gallery's account of him.
- **Copy states only what the Jesters' inputs or a cited source support.** The Jesters' inputs are `docs/inputs/`, their comments on #6, and what a Jester (mbelmear is Michael) writes in the originating ticket's body or comments; #123's review called "Michael's favorite painting" invented, though Michael's ticket said it. No invented facts about a Jester, Redeemer, or a Fool, even for a joke, and Scripture is quoted from the ESV (`docs/spec.md`, Content). The drafts before 2026-11-03 gave Redeemer long sermons and strong coffee, said the show grew out of its hallways, and quoted Paul in the KJV.
- **A copy change updates every place `docs/spec.md` quotes or names the old copy.** Copy the spec quotes counts as final (`AGENTS.md`, Content), so a stale quote reads as final wording that no longer exists. #103 changed the About heading and the 404 page, and the spec's summary still said "About explains why a jester".
- **Wording a third party requires word for word is final only once `docs/spec.md` quotes it**, with where it came from and the date it was checked, as Crossway's ESV notice is. It isn't the Jesters' to approve, so without the quote it falls outside both ways copy becomes final (`AGENTS.md`, Content). In #117 the notice first went in without `draft: true` and without the quote.
- **Copy shown on more than one page lives once**, in a content record each page reads, such as the Episode labels and length units. A page that needs copy another page already has moves it into a shared record, in place of a second copy.

## Workflows

- **A workflow that writes lasting state runs on the pull request that changes it, writing nothing.** A branch it pushes to, or a file nothing rewrites, keeps a first run's mistakes; a workflow started only by a schedule or the Run workflow button can't run before merge at all. Its pull request run does the real work against real inputs and uploads what it made as an artifact, so the PR shows it working. #121's Transcribe workflow does this: its PR run transcribed Episode 1 with Whisper, and the Transcript was read before the first one was saved for good.

## Secrets

GitHub's push protection (Settings → Advanced Security) refuses a push holding a key it recognises; these rules cover what it can't see.

- **A key lives in GitHub secrets, or as a Worker secret for the Worker**, and reaches code only as an environment variable a workflow step sets. Code reads it in build scripts or server-side modules, never under a `NEXT_PUBLIC_` name or in a client component, so no key reaches a page. What a key fetches (a link, a Transcript) may be published; the key may not. A key its service publishes by design may sit in secrets or Actions variables and still appear on the page, as Turnstile's site key and the Web Analytics token do.
- **A workflow hands a secret only to the steps that use it**, through `env:` on that step, and runs fork pull requests without secrets (`pull_request`, never `pull_request_target`). A build that lacks a key a deploy needs fails, as Turnstile's and analytics' do; one that lacks an optional key skips what the key does, as Spotify's lookup does for a fork's preview (#122).
- **A key never appears in output**: not in an error message, a log line, a `::warning::`, or a command line other processes can read. A script that needs one, or a token made from one, takes it through hidden input and passes it on stdin, as `scripts/spotify-key-wizard.sh` does; an identifier its service treats as public, such as Spotify's client ID, can be typed in the open.

## Browser tests

- **A browser test checks what the built page does, not what the Jesters' inputs hold today.** A count or fact about content that changes as their inputs arrive (how many Jesters have a headshot, which Listen links exist) lives once, in `src/content/content.test.ts`; the browser test checks behaviour that holds whatever those inputs say (every headshot shown loads). Fixed content, such as the style guide's specimens, can be counted where it's shown. In #26, `e2e/home-preview.spec.ts` pinned the headshot count beside the content test, and Michael's photo failed it in CI after Jest had already flagged the same change.
- **A test of absence proves it can fail.** A test that something doesn't happen (no animation, no request, no file fetched) passes just as well when it checks nothing, so a sibling case shows the same check finding the thing, or the PR shows it going red. #57's "fetches no rest file" matched `-rest` while the build names files `_rest`, until a sibling case that adds a letter found none.
- **A motion test proves it can fail.** A test that an animation finishes at once, or is skipped under reduced motion, follows the timing method in `docs/testing.md` (Browser tests (Playwright)), and its PR shows it failing with motion on (`reducedMotion: "no-preference"`). A test that runs before Motion loads passes either way, as the mobile menu's did until #60.
